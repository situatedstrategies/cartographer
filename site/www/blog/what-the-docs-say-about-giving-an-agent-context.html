What the docs say about giving a coding agent context

Every coding session starts from a blank page. The official guidance on filling it is more modest, and more useful, than the folklore.

By Team Cartographer · October 1st 2026 · 4 minute read

Ask ten developers how to set up a coding agent and you'll hear ten rituals. Write a huge instructions file. Paste in the whole architecture. Say it three times, in capitals. It's worth reading what the vendors actually put in writing, because the documentation is quieter than the advice around it. We read Anthropic's Claude Code documentation closely, and set it beside one recent study.

Every session starts fresh

The starting point in Anthropic's documentation is a plain one: each Claude Code session begins with a fresh context window.1 Two mechanisms carry knowledge across sessions. One is CLAUDE.md files, which the docs describe as instructions you write to give Claude persistent context. The other is auto memory, which the docs describe as notes Claude writes itself based on your corrections and preferences.1

So whatever the agent knows about your project at the start of a session, it knows because something was loaded. Nothing carries over by itself.

Context, not enforcement

The same page is careful about what these files can promise. It says Claude treats them as context, not enforced configuration.1 If you need an action blocked regardless of what Claude decides, the docs point to a PreToolUse hook instead. The best practices page makes the same split from the other side: CLAUDE.md instructions are advisory, while hooks are deterministic.2

That's a useful habit of mind. A line in an instructions file is a request, not a lock. If something must never happen, it needs a different mechanism than a sentence.

Short, specific and pruned

The documentation's advice on length is consistent. The memory page says that the more specific and concise your instructions, the more consistently Claude follows them.1 The best practices page goes further and gives a test for every line: ask whether removing it would cause Claude to make mistakes, and if not, cut it. It warns that bloated CLAUDE.md files cause Claude to ignore your actual instructions.2

The same page lists what to leave out, including anything Claude can figure out by reading the code, and file-by-file descriptions of the codebase. It lists what to put in: commands Claude can't guess, style rules that differ from defaults, and architectural decisions specific to your project.2

The reasoning behind the pruning is the docs' main constraint. In their words, Claude's context window fills up fast, and performance degrades as it fills.2 Context isn't free storage. Everything you load competes for room with the work itself.

Context also means a way to check

Not all context is background. The best practices page puts a different kind near the top: give Claude a way to verify its work, such as tests, a build, or a screenshot to compare.2 Their reasoning is that without a check the agent can run, "looks done" is the only signal available, and you become the verification loop.2

The page also recommends exploring and planning before coding, because letting Claude jump straight to coding can produce code that solves the wrong problem. It adds that if you could describe the diff in one sentence, you can skip the plan.2

A study that fits the pattern

The vendor docs are guidance, not measurement. A 2026 paper by Thibaud Gloaguen and colleagues tested the idea directly on repository context files such as AGENTS.md. The authors report that context files increase inference cost by over 20%, and that agents tend to follow the instructions in them.3 Their conclusion is that unnecessary requirements make tasks harder, so human-written context files should describe only minimal requirements.3

The abstract's wording on task success differs between versions of the listing, so we won't summarize it here. Read the paper if that number matters to you. The cost and instruction-following findings are enough for our point.

What we take from the reading

Three things stand out. First, the vendor and the researchers land in the same place: more context isn't better context. Second, the agent will tend to do what the file says, so every stale or unnecessary line is a small tax on every task. Third, a file is only as good as the last time someone checked it against reality.

That third point is ours, not the docs'. Treating the file like code, as Anthropic's page suggests, means reviewing it when things go wrong. But to review it, you need to remember what went wrong. Why did the agent ignore that rule? Which correction did you make three times?

A short checklist, drawn from the docs

  • Keep the instructions file short, and cut any line whose removal wouldn't cause a mistake.
  • Put must-never-happen rules in a mechanism that enforces them, not in prose.
  • Give the agent a check it can run, and ask for the evidence.
  • Revisit the file when behavior surprises you, not on a schedule.
